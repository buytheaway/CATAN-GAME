## Модель: определение карты и игровое состояние

**Map JSON** задаёт список клеток, а не готовые вершины/рёбра. **BoardState** содержит материализованные Tile, граф и размещённые фигуры. **GameState** добавляет игроков, ход, правила, pending, достижения и другие данные партии.

Реальный фрагмент [community_balanced_a.json](../../app/assets/maps/community_balanced_a.json), первые две клетки:

```json
[
  {"q": 0, "r": -2, "terrain": "fields", "number": 6},
  {"q": 1, "r": -2, "terrain": "forest", "number": 11}
]
```

В [base_standard.json](../../app/assets/maps/base_standard.json) те же позиции содержат `terrain: "random"`, `number: "random"`; terrain_deck/number_deck определяют состав.

### Координаты и IDs

- `q,r` — axial-координаты pointy-top гекса. Центр: `x = size * sqrt(3) * (q + r/2)`, `y = size * 1.5 * r`.
- Tile не имеет отдельного id-поля: **tile ID = индекс в массиве tiles**. Именно индекс используют adjacency, robber_tile/pirate_tile и команды `tile`.
- build_graph_from_tiles обходит тайлы в порядке JSON, вычисляет шесть углов (30 + 60*i градусов), объединяет совпадающие углы по quant_key с шагом 0.5 и выдаёт последовательные **vertex IDs**.
- **Edge ID = упорядоченная пара vertex IDs** `(min(a,b), max(a,b))`, а не самостоятельный номер. В JSON snapshot ключ — строка `"a,b"`, список edges — пары `[a,b]`.
- vertex_adj_hexes связывает вершину с индексами тайлов; edge_adj_hexes — ребро с индексами тайлов. Соседство тайлов можно получить по общему ребру, но отдельной таблицы tile_neighbors нет.
- Перестановка tiles в JSON меняет tile/vertex IDs. Они стабильны для одинаковых порядка координат и size; renderer не должен пересобирать/перенумеровывать граф.
- JSON `size` не выбирает engine size автоматически: build_game получает size отдельным аргументом; сервер использует 58.0.

Во всех нынешних пресетах одинаковые 19 координат, 54 вершины и 72 ребра. Sea остаётся гексом того же графа, а не дырой.

### Местность, номера, фигуры, порты

| Данные | Представление |
| --- | --- |
| Terrain | Tile.terrain: forest/hills/pasture/fields/mountains/desert/sea/gold; random существует только до материализации |
| Number token | Tile.number: integer или None; q/r/center/terrain/number отправляются в snapshot |
| Обычный ресурс | TERRAIN_TO_RES: forest→wood, hills→brick, pasture→sheep, fields→wheat, mountains→ore |
| Desert | Сухопутный тайл без обычного производства; обычный старт разбойника |
| Sea | Не производит стандартный ресурс; влияет на допустимость поселений/дорог/кораблей и пирата |
| Gold | Сухопутный тайл с номером; при enable_gold создаёт выбор обычного ресурса, не шестой ресурс |
| Поселение/город | occupied_v[vid] = (pid, level), level 1/2 |
| Дорога/корабль | occupied_e[edge] = pid / occupied_ships[edge] = pid |
| Разбойники/пират | robber_tile, robbers — tile indices; pirate_tile — index или None |
| Port | BoardState.ports = [((a,b), "3:1" или "2:1:wood" и т. п.)]; snapshot: [[[a,b], kind], ...] |

Port связан с двумя вершинами ребра. Торговый доступ определяется своей постройкой на одной из них. Видимый морской фон Base не означает наличие sea tiles: в Base их ноль. Fog/unknown, special scenario tokens, island IDs, стартовые зоны и exploration rewards сейчас не имеют отдельной модели.

## Что действительно рандомизируется

### Terrain

_materialize_tiles перемешивает terrain_deck через переданный RNG, затем по одному выдаёт значения только клеткам `terrain="random"`. Фиксированные клетки не трогает.

Все восемь поддерживаемых terrain могут находиться в пользовательской колоде, включая sea/gold/desert. Это выбор типа на **существующей координате**, не генерация новых координат или островов. В поставляемых Seafarers sea/gold заданы фиксированно; остальные выбранные позиции перемешиваются.

Если случайных клеток меньше колоды, используется только её начало. В simple_1/simple_2 стандартная 19-карточная terrain_deck выдаётся лишь 13/9 land-позициям: состав ресурсов и наличие пустыни зависят от seed. Нельзя считать этот режим сохранением полного стандартного resource balance.

### Number tokens

Аналогичный shuffle number_deck. У random-number клетки, материализованной как desert/sea, number становится None и карта из number_deck не расходуется. Gold может получить номер.

Есть seed-based shuffle. Нет алгоритма перестановки с запретом соседних 6/8, проверки соседства сильных чисел, локальной суммы probability weights или баланса ресурсов/стартовых вершин. Стандартная number_deck задаёт состав, но не проверяет размещение. В Base Standard при seed=1 обнаружены две пары соседних 6/8; в high_prob — шесть. community_balanced_a/b/c имеют ноль таких пар благодаря фиксированным данным.

### Ports

Явный `ports` используется без shuffle; даже `ports: []` отключает автопорты. Иначе _auto_ports:

1. Берёт рёбра с одним прилегающим тайлом.
2. Сортирует по углу середины ребра относительно (0,0).
3. Выбирает примерно равномерные позиции по count.
4. Перемешивает типы из deck и сопоставляет выбранным рёбрам.

**Позиции при одинаковой геометрии/count не случайны; случайны типы.** Это внешняя граница всей сетки, а не проверка land/sea coast. Все 12 текущих пресетов используют auto, обычно девять портов.

Ограничение подтверждено при seed=1:

| Seafarers preset | Ports на sea-only ребре | Ports без land на обеих конечных вершинах |
| --- | --- | --- |
| simple_1 | 5/9 | 4/9 |
| simple_2 | 8/9 | 7/9 |
| gold_haven | 4/9 | 2/9 |
| pirate_lanes | 4/9 | 3/9 |

Последняя колонка означает невозможность обычной постройки для доступа к этим портам. Renderer сможет показать фактические данные, но новый рисунок не исправит алгоритм. Для сложных островов explicit ports обходят auto-расстановку; число/береговая допустимость портов требуют отдельной проверки.

### Shape

Всегда берётся список q/r из JSON. Общий builder способен материализовать больший остров, раздельные острова или архипелаг из custom JSON, но не выбирает такую форму автоматически и не проверяет её пригодность для полноценного сценария.

Все 12 поставляемых форм — 19 одинаковых координат. Во всех четырёх Seafarers land остаётся одной связной компонентой: готового multi-island preset нет.

### Seed

build_game создаёт `random.Random(seed)` и передаёт один поток в materialization/ports, затем перемешивает development deck. При одинаковых данных, порядке tiles, size, seed и версии алгоритма карта повторяется. Один seed без map definition/версии не является полным идентификатором карты.

Seed задаёт terrain shuffle, number shuffle и порядок типов auto ports. Не задаёт shape, положения auto ports или фиксированные terrain/number/explicit ports. Изменение предыдущего RNG-потребления меняет последующие shuffle.

В multiplayer _start_match создаёт seed через secrets.randbits(64), но затем отдельно перемешивает dev_deck через SystemRandom. Dice тоже серверные и независимые от map seed. Клиент seed не получает. Поэтому reproducible map не равна reproducible multiplayer game.

## Map editor и custom JSON

**Редактора в текущем проекте нет.** Пункт Map Editor есть только на старом lobby design reference.

| Возможность | Сейчас |
| --- | --- |
| Добавить/удалить hex, рисовать islands | Нет UI |
| Менять terrain/numbers/ports интерактивно | Нет UI |
| Сохранить созданную карту из редактора | Нет UI |
| Написать JSON внешним редактором | Да |
| Импортировать custom JSON в web/desktop | Да |
| Создать GameState из такого JSON | Да, при успешном build_board_from_map |

Offline desktop: ModeSelectDialog._on_load_map → GameConfig.map_path → start_game → ui_v6.build_board → rules.build_game. Online desktop: LobbyWindow → NetClient.set_map; web: LobbyPage FileReader → WSClient.setMap. В комнате загрузку принимает только host до начала матча.

В desktop expansion-selector Seafarers disabled/coming soon, а список map presets уже содержит морские карты. Реальные flags берутся из JSON rules; selector не является гарантией полноты expansion.

validate_map_data проверяет форму/часть типов, диапазон обычного number и названия явно заданного terrain, но не игровую пригодность карты. Не проверяет уникальность q/r, содержимое random decks, достаточность/точность их количества, 6/8 adjacency, островной баланс или полноценные сценарные правила. explicit port edge проверяется в build_board_from_map, не при первичной загрузке.

В памяти подтверждено: terrain_deck=["lava"]/number_deck=[7] и две клетки с одинаковыми q/r проходят validator/materialization. Импорт принятого JSON ещё не доказывает корректность игровой карты. Fog, exploration, island rewards, специальные цели и токены engine не реализует; такой terrain не появляется от добавления arbitrary JSON field.

Отдельная граница multi-island gameplay: can_place_settlement(require_road=True) ищет только свою occupied_e road и не учитывает occupied_ships. Новая геометрия островов сама по себе не делает заселение через морской маршрут полноценной поддерживаемой механикой. Смешанные/закрытые маршруты и move_ship также остаются частичной реализацией; Board3D не должен маскировать это собственными правилами.

## Web rendering: порядок исполнения

1. **LobbyPage:** выбор пресета → WSClient.setMap(mapId); файл → FileReader.onload → JSON.parse → WSClient.setMap(undefined, data).
2. **WSClient.setMap:** отправляет `{type:"set_map", map_id?... , map_data?...}`.
3. **server_mp.websocket_endpoint / set_map:** проверяет host/lobby, validate_map_data для custom; Room хранит selected_map_id/selected_map_data и rules metadata.
4. **start_match → _start_and_notify → _start_match:** создаёт server seed, передаёт selected map в rules.build_game.
5. **rules.build_game:** map_data → map_path → preset по приоритету; maps.build_board_from_map → _materialize_tiles → board_geom.build_graph_from_tiles → ports → BoardState; parse_rules_config → GameState.
6. **_send_match_state → _snapshot_state:** serialize.to_player_dict делает персональный view; сервер добавляет you_pid и _legal_moves.
7. **net_protocol.match_state_message → _send:** JSON с room_code, match_id, tick, state через WebSocket.
8. **WSClient.handleMessage / match_state:** проверяет room/match/tick, сохраняет MatchState, обновляет youPid и вызывает onMatchState.
9. **App.onMatchState → setMatch:** новый React state; App передаёт match в GamePage.
10. **GamePage:** передаёт match.state/youPid/selectedAction и callback client.sendCmd в BoardView.
11. **BoardView:** tiles/vertices/edges/occupied_*/ports → SVG; calculateBounds подгоняет область под данные; preset-specific координат нет.
12. **Клик:** vertex → place_settlement/upgrade_city; edge → place_road/build_ship/move_ship; tile → move_robber/move_pirate. Callback → WSClient.sendCmd → server _apply_cmd → rules.apply_cmd → новое состояние → шаг 6.

TypeScript: RoomState описывает map catalog/выбор; MatchState содержит GameState с players/private fields; BoardView.types.GameState описывает geometry/pieces/pending/legal. Wire уже содержит q/r и vertex_adj_hexes, хотя текущий BoardView Tile/GameState эти поля не объявляет. Для использования потребуется описать существующие поля в TS, не обязательно менять серверный контракт.

Renderer строит поле из данных и не обязан знать preset. Сейчас специализацию 2:1-порта UI не рисует: portRatioLabel показывает только ratio, хотя kind уже содержит ресурс.

## Готовность к Board3D

**Геометрии snapshot достаточно для 3D-представления существующих открытых карт.** Сохраняется путь GameState → player-specific snapshot → React → renderer. Не требуется менять правила, JSON-пресеты или общий Python engine ради объёмных tiles/figures.

coordinates.ts может преобразовывать уже готовые (x,y) в (x/scale, elevation, y/scale), брать midpoint/направление edge и позицию vertex. Hover/click несёт исходные tile index, vid или [a,b]. Визуальная высота не меняет topology.

Правила остаются на сервере/в движке. Board3D отображает state/готовые targets и вызывает callbacks существующих команд. Выбранное действие и двухшаговый выбор ship лучше держать в controller выше renderer; это предложение границы, не выполненный refactor.

### Недостающие данные для полностью rule-free interaction

1. **Полная доступность placement для выбранного действия:** legal сейчас учитывает topology/phase, но не ресурсы/запас фигур; не представляет отдельно free Road Building до roll. Подтверждён пример: city в legal.cities, при исполнении — Not enough resources.
2. **Допустимые источники и цели move_ship** (цели зависят от выбранного source). Сейчас BoardView выводит их приближённо, _legal_moves их не выдаёт.
3. **Допустимые tile targets для каждого robber/pirate и victims по выбранному target**, если UX предусматривает выбор жертвы. Сейчас цели вычисляет клиент по terrain, а victims engine проверяет при исполнении.

Для чисто визуального прототипа это не blockers. Для точной подсветки всех допустимых действий понадобится расширить server-produced legal view, сохранив authority и проверку в apply_cmd. Legal, зависящий от личной руки, должен выдаваться соответствующему игроку: сейчас _legal_moves получает только game и прикладывает одинаковые topology lists ко всем views. Fog/visibility потребует дополнительного scenario state и скрытия неизвестных terrain/number сервером, если такая механика отдельно будет реализована; сегодня в поддерживаемых картах fog нет.

## Будущий Random Map Generator — предложение, не реализация

Три режима следует различать:

- **Preset:** финальная фиксированная карта, без неожиданного auto shuffle.
- **Shuffle:** фиксированные coordinates и land/sea mask; явно выбранные terrain/numbers/port types перемешиваются с сохранением конфигурации и ограничений.
- **Generated:** seed сначала создаёт координаты/острова, затем содержание; готовый результат передаётся существующему map loader.

Нынешние presets фактически смешивают первые два режима. Их поведение нельзя автоматически менять под новые названия.

```text
seed + generator_version + scenario/profile + constraints
  → topology
  → terrain distribution
  → number placement
  → placement/balance validation
  → ports
  → scenario validation
  → final MapDefinition (schema v1, насколько её хватает)
  → существующий build_board_from_map / build_game
```

Предлагаемое место — отдельный модуль рядом с engine/maps.py. Generator возвращает полностью материализованные значения; loader остаётся потребителем, а React только отображает итог. Для multiplayer генерация/валидация принадлежит серверу.

| Этап | Ответственность / ограничения |
| --- | --- |
| Topology | Unique q/r; заданные размеры, land/sea mask, число островов, расстояния и связность; пригодные стартовые land-вершины |
| Terrain | Точные квоты ресурсов, desert/gold/sea и закреплённые клетки; правила профиля для пустынь/золота, а не универсальная произвольная норма |
| Numbers | Номер только на производящей клетке; заданный number multiset; политика 6/8 adjacency по профилю |
| Balance | Вес номера = 6-abs(7-number) исходов из 36; сумма/разброс по ресурсам, островам и стартовым вершинам; допустимые диапазоны, не обещание идеального равенства |
| Ports | Настоящая береговая land/sea boundary (либо внешний берег land-only карты), доступные land endpoints, spacing/count/types; не нынешняя len(adj)==1 эвристика |
| Scenario | Разрешённые start islands/zones, pirate sea position, gold quotas, цель/правила выбранного сценария; непредставимые/неподдержанные механики отклоняются явно |
| Finalization | Зафиксировать порядок tiles/IDs; построить graph до explicit edge ports; повторно validate; сохранить seed/version/config и итоговый JSON |

Детерминированность требует версионированного алгоритма и стабильных независимых RNG-потоков для topology/terrain/numbers/ports; иначе добавление shuffle меняет остальные результаты. Нужны ограниченный бюджет попыток/поиска и понятный отказ при несовместимых constraints, вместо бесконечного retry.

Базовый Shuffle ближе к готовности: есть materialization и graph. Generated требует topology builder, scenario profiles и содержательной валидации; это отдельная задача, не небольшой checkbox. Arbitrary multi-island геометрия уже представима, но это не устраняет известные ограничения Seafarers routes/scenarios.
