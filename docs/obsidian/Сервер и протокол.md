## Explicit lobby closure — Room Lifecycle Phase 1

Implemented/focused-tested **2026-10-12**. React `LobbyPage` confirmation → `WSClient.closeLobby()` → validated `close_room` → `_dispatch` session context → room lock/current controller → `_close_lobby` → `Coordinator.lobby_closure` → `Repository.lobby_closure` → candidate/receipt COMMIT → `_finish_lobby_close` → public notice. Protocol VERSION stays 1; the additive intent is:

```json
{"type":"close_room","room_code":"ABC123","request_id":"unique-operation-id","expected_match_id":0}
```

All four fields are required; extra identity/credential fields are rejected. Guest hosts prove ownership through the already-bound controlling socket and a valid nonrevoked durable seat token. Account hosts require the matching current account session/membership. Non-host, stale/expired/revoked controller and wrong-room requests fail without a closure write. The durable guard additionally requires `status=lobby`, `match_no=0`, no current or historical Match and the expected durable revision. Active and finished matches cannot be closed by this intent.

Closure and creation take the same transaction advisory lock. `closed`, `closed_at`, guest-token revocation and the operation receipt commit atomically; concurrent origin/global capacity is released only at COMMIT. Accepted-creation rate consumption remains. Then RAM registration/controllers are fenced and connected participants receive `{"type":"room_closed","room_code":"ABC123","request_id":"unique-operation-id"}`. The request ID may be absent when a delayed uncertain-COMMIT resolution finishes closure. The notice contains no hand, development card, token or snapshot. Publication failures cannot undo durable closure.

No success frame before COMMIT. Pre-COMMIT failure preserves the lobby and permits the same request ID after valid reconnect; unresolved COMMIT keeps mutations fenced until authoritative resolution. Already-closed requests return ordinary unavailable/not_found/forbidden without a second write; closure never grants a replay success to revoked ownership. After a lost notice, generic reconnect refusal clears stale frontend controls. Closed rooms are absent from recoverable IDs, Active Games and guest inspection, and cannot join/start/reconnect after restart. Account sessions stay valid for other rooms. `leave_room`/socket disconnect changes connection presence only; valid existing ownership remains reconnectable. No automatic expiry/deletion or active-match abandonment is added.

Evidence — [local/dispatch tests](../../tests/test_lobby_lifecycle.py), [PostgreSQL lifecycle tests](../../tests/test_lobby_lifecycle_postgres.py), [Chrome runner](../../web/e2e/lobby-lifecycle.cjs). Final executed suites and limits — [[Project State]], [[Architecture Decisions#ADR-022 — Explicit host-owned pre-match lobby closure]].

## Room creation quotas — SEC-03

Implemented/focused-tested **2026-10-12**: `create_room` takes the RoomManager creation mutex, derives its canonical peer through shared `auth.security.client_ip` (the same policy as SEC-04 HTTP auth), then enters `Coordinator.room_creation` → `Repository.room_creation`. Never read protocol-supplied identity/forwarding as a budget key. In durable mode, a transaction advisory lock serializes metadata count/check before Room/player/token allocation. `Repository.save` inserts using that same session; COMMIT → RAM registration → controlling-socket bind → room_state → credential. Rejected admission performs no insert/update/credential/publication and retains the old controlling connection; it returns ordinary `error`, keeps the socket open, and does not set persistence.ready false.

Defaults: 20 accepted creations/IP per rolling 600 s; 20 lobby rooms/origin; 1000 durable lobby rooms globally. All status-lobby rooms count, including offline/Test/legacy NULL-origin/unloaded rooms. Starting a match releases concurrent lobby capacity; recent creation consumption remains. Guests and accounts share network budgets; join/reconnect/Continue/rematch remain ownership-authorized and uncharged. These limits supplement, not replace, authentication/publication/gameplay validation.

Existing error shape `{type:"error", code, message, detail?}` is retained. New codes: `room_creation_rate_limited` with conservative `detail.retry_after_seconds=window`; `ip_lobby_limit_reached`; `lobby_capacity_reached`; `room_creation_busy` only for bounded explicit-memory tracking saturation. Frontend's existing string-code `ServerError`/onError displays these messages; WS schema/client code is unchanged. Limit priority is global → origin lobby → creation rate, followed by memory tracking capacity. Retry-after concerns rate exhaustion only; it does not promise a persistent lobby slot will expire.

Migration sec03a001 stores private origin digest outside GameState/snapshots, preserves legacy NULL without provenance inference, and supports exact ordinary recovery. No gameplay rules execute on admission/recovery, no Fog exposure or changed F1/F2 constraints, no RAM fallback when DB is unavailable. No automatic expiration/deletion or offline credential invalidation is added. Retention, NAT/IPv6 limitations, config and test scopes — [[Deployment#Room creation admission — SEC-03]], [[Architecture Decisions#ADR-021 — Durable room admission, conservative lobby retention]], [[Project State]].

`leave_room`/disconnect retains status lobby and ownership; expired credentials or elapsed `expires_at` do not change durable admission counts. Start Match changes status to in_match, freeing a lobby reservation. **Historical SEC-03 checkpoint:** internal `close_room` had no public/admin command and must not be used on arbitrary active matches. Room Lifecycle Phase 1 now provides the guarded public intent above; automatic never-started retirement remains planned. Repeated create/leave without explicit closure/start can still exhaust reservations.

### Balanced dice — balanced_v1

Random остаётся двумя независимыми secrets faces. Balanced использует приватный Room.dice_bag: все 36 ordered (a,b), a/b=1..6, secure shuffle, draw без replacement. После 24 успешных draws остаётся 12; следующий Roll заменяет остаток новым полным bag, не смешивает его. Полный bag имеет weights сумм 1,2,3,4,5,6,5,4,3,2,1; 24 draws имеют эти веса в ожидании, но не гарантируют точную гистограмму любых 36 последовательных бросков. Алгоритм не зависит от pid/ресурсов. В Room.dice_algorithm хранится version balanced_v1.

Удалённая комната не возобновляет его из старого scheduler списка. Автоматический TTL/retention комнат не добавлен.

turn_timer в personal snapshot: `{pid, deadline_ms, server_time_ms, remaining_ms, stage}` либо null. Deadline принят сервером; remaining основан на monotonic clock, поэтому перевод wall clock не продлевает ход. React интерполирует remaining через performance.now только для отображения. Manual Roll не начинает полный timer заново. Reconnect получает текущий deadline/remaining.

При expiry без rolled выполняется прежний authoritative Roll и 20s grace; с rolled выполняется прежний End. Любой pending_action или положительный free_roads блокирует авто-действие: stage=blocked, UI Action required, никаких случайных ресурсов/целей/жертв. После explicit resolution безопасная expiry policy продолжается. Manual End может отказаться от остатка free roads по уже исправленному engine lifecycle. Локально открытые, ещё не отправленные Plenty/Monopoly forms не являются server pending; сервер не знает об их выборе. Неожиданный отказ auto-command переводит timer в stopped вместо бесконечного повтора.

Auto-actions увеличивают room.tick, используют тот же executor и personal snapshots, не расходуют client seq/cmd_id. Due timer обрабатывается также перед client cmd: отдельное deadline-событие может произойти перед отклонённой командой, но сама rejected command остаётся atomic. После await снова проверяется WS ownership. Existing consumed-on-rejection contract не меняется.

### Chat and bank

Chat сохраняется в Room, отдельно от GameState и gameplay/transport log. `_append_chat` принимает 1..500 исходных символов, trim, не пустое; максимум 5 сообщений/10s на PlayerSlot (reconnect не сбрасывает rate window). Публикует `{id,name,color,text,sent_at_ms}`, хранит последние 50. Название/цвет фиксируются на момент отправки; автор не переносится на новый pid после rematch. id/chat_revision монотонны в комнате, timestamp не используется для ordering.

`chat_state {room_code,chat_revision,chat_history}` обновляет обоих клиентов; room_state/reconnect тоже содержит history. WSClient сохраняет более новую chat_revision при старом presence room_state. React отображает plain text без HTML/Markdown. Чат не проходит cmd sequence и не мутирует game. Никакого полноценного engine event feed не добавлено: Game Log показывает существующий log, Chat — только сообщения.

`_snapshot_state` продолжает to_player_dict и добавляет public room_settings, turn_timer, players[].color. Visible (default) добавляет копию bank с точными counts. Это принятая casual policy, которая в двух игроках допускает вывод состава чужой руки из банка/своей руки. Hidden не добавляет bank, оставляет прежние bank_available и приватную projection. Foreign res/dev cards/active hidden VP, seed, RNG bag и private choices сохраняют прежние ограничения; development deck и даже его count остаются hidden — отдельной публичной policy нет.

VERSION=1; новые поля/типы additive. Нужны согласованные web/backend images; старый Qt может игнорировать поля, его settings/chat/timer UI и цветовое соответствие отдельно не реализованы/не проверены. ## Сообщения

[net_protocol.py](../../app/net_protocol.py) содержит `validate_client_message` и функции создания сообщений.

| Направление | Типы |
| --- | --- |
| Клиент → сервер | hello, create_room, join_room, reconnect, leave_room, set_map, set_settings, set_color, chat, start_match, rematch, cmd |
| Сервер → клиент | hello, room_state, chat_state, reconnect_token, match_state, cmd_ack, error |

`cmd` — конверт. Вложенное поле `cmd` содержит игровое действие, например `{type: "roll"}`. `match_id` различает матчи, `seq` задаёт порядок действий игрока, `cmd_id` помогает распознать повторы.

`websocket_endpoint` проверяет сообщение, находит комнату и pid соединения, проверяет идентификаторы и вызывает `_apply_cmd(room, pid, cmd)`.

`_apply_cmd` возвращает объект ошибки или None при успехе. Движок возвращает события, но сервер сейчас не рассылает их отдельно: он вызывает `_send_match_state` и отправляет полный снимок через `match_state_message`.

`_snapshot_state(game, room, pid)` получает персональный JSON через `serialize.to_player_dict` и добавляет you_pid/legal/dice/roll_count/room_settings/turn_timer/public colors и bank только при Visible. `_broadcast` используется для публичного room_state; `_send_match_state` создаёт отдельный снимок каждому подключённому pid. Все представления фиксируются до первого await, чтобы один update имел одинаковый tick у получателей. Перед отправкой проверяется, что соединение всё ещё владеет слотом и матч не сменился. Все комнаты хранятся в памяти процесса.

## Lobby map ordering

Verified 2026-10-04 — отдельный узкий lobby fix после Board3D Phase 1. Room.selected_map_id/data/meta/rules — source of truth. Новый map_revision=0 при создании комнаты; успешный set_map увеличивает его на один перед broadcast. Повторный выбор того же ID тоже увеличивает revision: custom JSON может иметь одинаковое имя при разных данных. Presence, reconnect и Start не меняют map_revision; новый match не сбрасывает её. Это версия выбора карты, не GameState.tick или общая версия комнаты.

room_state содержит обязательный integer map_revision. Новый Web client отбрасывает меньшую revision той же комнаты и room_state другой выбранной комнаты. В рамках одного revision map fields неизменны; presence broadcasts с той же revision принимаются. Серверные проверки host/lobby/map validation сохранены. VERSION остаётся 1: поле additive, desktop читает прежние поля и игнорирует новое. Обновлённый web требует сервер с map_revision; существующий Compose собирает/запускает их вместе.

Форма set_map не менялась. При отказе сервер дополнительно возвращает detail.request_type="set_map", включая schema errors, чтобы клиент отличал завершение map request от чужой ошибки. Проверенные invalid ID/data и unauthorized set_map не меняют выбор/revision. Новая успешная карта подтверждается room_state с большей revision; отдельный тип ACK/request ID не вводится.

WSClient отправляет один map request одновременно; последующие выборы заменяют единственный queued request. Подтверждение/явный map rejection завершает in-flight, затем отправляется последний queued выбор. Selector показывает последний pending ID до окончательного подтверждения, Start ждёт его. Pending не сохраняется/replay при disconnect или смене room; token reconnect восстанавливает только серверный выбор. Ownership, cmd sequence и match snapshots не менялись.

160 pytest и 48 web tests проходят. Live WS tests проверяют A→B, общий final revision, Seafarers snapshot при Start, token reconnect, отказ без смены revision и новый room=0. Production browser дополнительно проверил фактическое отображение двух React-клиентов при задержке ACK/повторе stale room_state, custom JSON и 3D Gold Haven. UI-часть — [[React интерфейс]], renderer scope — [[plans/board3d]].

## Slot ownership and match composition

`join_room` занимает свободное место только в lobby; совпавшее имя не даёт reconnect и отклоняется. Имя уникально в комнате. `reconnect` требует существующий bearer token; `bind_player` отвязывает прежнее соединение от комнаты/pid. Закрытие старого сокета не отключает нового владельца. Это минимальное владение слотом, не account authentication.

React `LobbyPage.onJoin` вызывает loadToken для выбранной room/name/server URL и инициирует Join. `WSClient.sendJoinIntent` выбирает reconnect при наличии соответствующего token либо join_room без него; helper используется и при открытом WS, и после открытия queued Join, и при восстановлении соединения. loadToken очищает предыдущий token до чтения cache; прямой Join другой комнаты также не переносит чужой token. Phase 1C мигрирует старые `catan_reconnect_<roomCode>_<name>` в versioned `catan_recent_games`; pending commands/pid/GameState туда не сохраняются. Host начинает создание новой комнаты без прежней reconnect identity.

Пока ожидается результат reconnect, forbidden/not_found очищает его token в памяти и соответствующий cache, передаёт ошибку UI и не запускает Join по имени. Следующее автоматическое открытие WS не повторяет отклонённый token. Пользователь может явно начать новую попытку. Серверная ownership-модель и protocol shape этим исправлением не менялись. Проверки: [wsClient.test.mjs](../../web/tests/wsClient.test.mjs) и test_web_join_reconnect_against_live_server в [test_server_authority.py](../../tests/test_server_authority.py).

Каждый `_start_match`, включая rematch, включает только named+connected slots и требует минимум двух участников. При первом старте host должен быть подключён. Rematch запускает подключённый host; если он отключён, `_rematch_host_pid` выбирает первого подключённого участника. Только этот кандидат может запустить rematch, и host_pid меняется после успешного build_game. При недостаточном составе прежние GameState/match_id/tokens сохраняются.

Старт обновляет компактные pid, conn.pid и host_pid; исключённые привязки отвязываются. `_start_and_notify` отправляет room_state → reconnect_token → match_state. GameState.max_players равен фактическому составу; Room.max_players остаётся вместимостью комнаты. Новый join после старта запрещён; боты не добавляются. match_id увеличивается, tick и slot seq/cmd_id history сбрасываются.

До rematch token отключённого игрока продолжает восстанавливать прежний слот/матч. Если игрок подключился до старта, он входит в новый состав. Если остался отключённым, его слот удаляется при старте и token больше не принимается; он не может получить чужой pid после уплотнения. Token сохранившегося участника остаётся действительным с новым pid. Token-based reconnect по-прежнему отзывает старую WS-привязку, а закрытие прежнего сокета не отключает нового владельца.

## Private snapshot contract

- Свой player: res, dev_cards, resource_count, dev_count, полный личный vp.
- Чужой player: pid/name/knights_played, resource_count/dev_count и публичный vp; res/dev_cards отсутствуют. Во время игры vp не включает скрытые VP-карты. После game_over все players.vp содержат итоговый total VP, включая проигравших; res/dev_cards соперников по-прежнему закрыты. Это данные для будущего экрана результатов, отдельного final-score поля не требуется.
- discard_required и pending_gold содержат только собственную запись; уже выполненный discard не повторяется в private choice. pending_victims доступен pending_pid. free_roads/dev_played_turn содержат только свой pid.

Spectator API не добавлен. to_dict остаётся trusted/offline форматом; его нельзя рассылать вместо to_player_dict. Web/desktop согласованы с этим контрактом, старые сторонние клиенты требуют адаптации. В reconnect_token добавлен match_id; network VERSION пока 1.

## Private publication authorization — F1

Verified **2026-10-08**. Personal projection alone does not authorize its recipient. Previously `_send_match_state` checked active_ws and account_socket_valid, whose guest branch returns true; an already-open guest socket could therefore keep receiving its private hand after token expiry/revocation even though `_owns` denied commands. Both `_send_match_state` and `_send_match_state_to` now use `_publish_match_state` in [server_mp.py](../../app/server_mp.py).

The publisher captures the connection, stable RoomPlayer ID, pid and match_id with the frozen personal view. It checks the registered/current Room and controlling socket, `_owns` (guest expiry/revocation or account ownership/session expiry), and account validation. It rechecks captured recipient identity and current authorization immediately before passing the encoded frame to WebSocket; no extra scheduled send task sits after that final check. Takeover, pid changes, rematch or Room replacement discard an obsolete frame rather than sending a different player's view or disconnecting a new controller. Broadcast views still share the same committed GameState/tick and retain the existing private-field projection.

Production callers hold Room.lock through publication, serializing claim/reconnect/rematch and durable guest credential changes. For an account connection, the existing authorize_transaction PostgreSQL session/user SHARE locks remain held through the private send. A concurrent logout/revoke or user-disable UPDATE must commit first (publication denied), or wait for the already-authorized frame. Account ownership does not depend on the old guest token, including after claim with matching connection_nonce. Command authorization is unchanged.

Failed current ownership synchronously removes active_ws and marks connected=false before sending an error and closing 4401. A stale queued frame for a different binding is simply dropped. Persistence/session unavailability fails closed with 1013; existing proof/session records are not renewed, revoked or replaced by a RAM-only path. Error/close/send failures and the encompassing two-second async timeout leave the controller fenced. GameState, tick and command sequence are not changed by this refusal.

Limits: the existing single-worker authoritative Room model remains; direct out-of-band SQL changes to guest seat records are not a live revocation API. Publication ordering refers to handing an authorized frame to WebSocket, not its eventual delivery: a frame already sent before revocation cannot be recalled. Account publication adds one short PostgreSQL authorization transaction and may delay a concurrent logout while a bounded send is in progress; high-load performance was not benchmarked. No frontend/build/scenario rerun, schema migration or protocol shape change for F1.

## Sequence semantics

Историческое имя `last_seq_applied` означает **last consumed sequence**, а не только успешно применённые действия.

1. Неверный envelope/ownership/room/match/no_match или gap (`seq > expected_seq`) не расходует номер.
2. Очередная команда действующего матча получает engine success либо RuleError. Seq/cmd_id учитываются на candidate под room lock; в durable mode COMMIT предшествует изменению RAM и подтверждению.
3. RuleError: error + ACK applied=false; GameState и room.tick неизменны, seq использован.
4. Success: candidate tick/head/seq/receipt durable committed, затем RAM tick и персональные snapshots + ACK applied=true.
5. Уже consumed seq/известный cmd_id → ACK duplicate=true без повторного применения. Хранится LRU 256 IDs; старые seq также отсекаются счётчиком. Duplicate ACK не воспроизводит исходный success/error, но подтверждает, что intent не применяется снова.
6. Клиенты удаляют pendingCmd по ACK, включая applied=false; при reconnect удаляют seq ≤ last consumed и повторяют только оставшиеся с тем же cmd_id. Повтор попытки после отказа — новая команда/номер.
7. Очереди и seq привязаны к room_code+match_id. Новый матч сбрасывает их; token содержит match_id. Неизвестный/поздний ACK и старые snapshots не откатывают новый матч.

Сохранение consumed-on-engine-rejection предотвращает бесконечный replay незаконного действия. Success-only numbering создал бы gap после отказа; семантика сохранена и покрыта тестами. Phase 1B durable mode теперь восстанавливает комнату/consumed seq после restart; memory-only mode этого не делает.
