# Documentation Policy

## Source of truth

| Вопрос | Источник |
| --- | --- |
| Что делает система сейчас? | Код; заметки архитектуры проверяются по коду |
| Как должна играть? | [[Спецификация пользователя]]; краткие правила — навигация по ней |
| Какие ограничения намеренны? | Принятые [[Architecture Decisions]] |
| Какое состояние и приоритет сейчас? | [[Project State]] |
| Какой дизайн рассматриваем? | [[Design System]], с явным статусом каждой идеи |
| Как проверяли ранее? | [[Результаты аудита]] и исходный отчёт с датой |

Текущие инструкции пользователя имеют приоритет. Код, противоречащий правилам, может содержать баг. Не переписывать правила под баг; описывать расхождение. Неуверенность в заметке требует сверки с соответствующим кодом.

## Before changes

Прочитать Главную, Project State, существующую архитектурную карту, ADR и тематические заметки. Проследить реальный путь исполнения. Для крупной задачи использовать [[plans/README|раздел планов]]. Не считать план разрешением выполнить его.

## After substantial changes

- Обновить Project State: фактическое поведение, проблемы, ограничения проверки и следующий этап.
- Если менялась архитектура — соответствующий существующий документ слоя/пути.
- Если менялся протокол — Сервер и протокол и Состояние игры.
- Если менялись UI-конвенции — React интерфейс, Стили и визуальные границы, Design System.
- Если пользователь менял правила — спецификацию и связанные краткие правила.
- Важные архитектурные решения — ADR с причиной и последствиями.
- Перед завершением сверить затронутые заметки с фактическим кодом и доказательствами проверок: пути исполнения, API/schema, статус возможностей, совместимость и оставшиеся ограничения. Обновления текста без этой сверки недостаточно.

Не менять документы ради форматирования кода. Не создавать новые копии существующих справочников. Устаревший historical audit сохраняет дату и доказательства, а не превращается в актуальную сводку.

## Content rules

Документация описывает текущее поведение, намеренное поведение и причины важных решений. В ней нет полных переписок, дневника каждого commit, истории typo и предположений под видом фактов. Не создавать memory_dump, everything_about_project, session-log или огромный codex_memory.

Для facts указывать проверку; для требований — источник; для concepts — статус. У Design References отдельно отмечать фактически просмотренное изображение, пожелание пользователя и неутверждённую интерпретацию. Не придумывать окончательные токены дизайна.

Статус реализации и статус проверки указывать отдельно:

- **Implemented:** поведение существует в текущем коде; это само по себе не доказательство полноты проверок.
- **Tested:** названы дата, тест/acceptance и проверенные границы. Не распространять результат на непроверенные клиенты, сценарии или production.
- **Partially implemented:** явно перечислены работающая часть и недостающие механики.
- **Planned:** согласованное или предлагаемое будущее поведение без заявления о реализации.
- **Known broken:** подтверждённый отказ или несоответствие с доказательством; зелёный другой suite не закрывает проблему.

**Historical / superseded** обозначает контекст прежнего checkpoint, а не текущий статус. Сохранять важные ADR и старые результаты с датами, указывая заменившее решение/реализацию. Latest verified — последний реально выполненный набор; при документационной задаче не приписывать ему новую дату запуска или увеличенное число тестов.

## Validation

Проверять внутренние wiki-links, anchors и обычные ссылки. Изображения должны существовать до добавления ссылки/embed; ожидаемый путь писать обычным code-текстом. После изменения документации сверить, что код не затронут, если задача только документационная. Не обновлять Last verified без описания того, что реально проверено.
